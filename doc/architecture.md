# How it is built

This page is for someone changing the code rather than using it. Everything
before it describes the workbench from the outside; this is the seam map — what
each half owns, what crosses between them, and where a change to one half
forces a change to the other.

Three documents are the authority behind it, and are worth having open beside
it: `ql-backend/DESIGN.md` for why the service is shaped the way it is, cited
to QuantLib's own source; `ql-backend/HANDLERS.md` for every frame and field
it accepts; and `PLAN.md` for this client's design record, including what was
deliberately not built. This page is the map. Those are the terrain.

## Two programs, one schema

```{figure} images/two-programs.svg
:alt: Two panels side by side. ql-frontend, a browser tab, is four stacked layers: components, store, operations and WireClient. ql-backend, one process, is four stacked layers: gateway, supervisor, worker and Session. A binary WebSocket joins WireClient to the gateway, carrying one ClientFrame out and one ServerFrame back. Below both, a band for proto/quantlib/v2, the one schema each side generates its bindings from.
:width: 100%

Each half in the order a request meets it. The only thing that crosses is a
frame, which is why the schema rather than the code is the contract between
them.
```

The two repositories share `ql-protobuf`, pinned as a submodule in each. Nobody
writes a frame by hand and nobody commits a generated binding: the C++ side is
generated by `protoc` from `CMakeLists.txt`, the TypeScript side by `npm run
gen` into `src/gen/`, which is gitignored. One source of truth, and no stale
copy to disagree with it.

WebSocket already delimits messages, so a frame carries no length prefix — one
serialized `ClientFrame` or `ServerFrame` per binary message. Every request
carries a `request_id` the client allocates and a `session_id`, and every
request ends in exactly one terminal frame.

## The service side

Four layers, and each one exists because of a constraint rather than a
preference.

| Layer | Owns | Why it is separate |
| --- | --- | --- |
| **Gateway** (`src/gateway/`) | The uWebSockets loop, sockets, correlation ids, backpressure, the `Origin` check, the grace timers | It is the only thing that touches the network, and the only thread the supervisor is ever called from |
| **Supervisor** (`src/session/supervisor.*`) | Every `SessionLog`, worker placement, cancel-by-kill and the replay after it | Recovery is policy; it is testable against a fake process host |
| **Worker** (`src/session/worker.*`) | One thread, one session, a request queue | QuantLib's session isolation is per *thread* |
| **Session** (`src/session/session.*`) | The live object graph, and the dispatch from proto to engine | It is the only place QuantLib appears |

**The event loop is single threaded, and that is load-bearing.** Everything
that touches the supervisor runs on it, which is what lets `sessions_` and
`workers_` be mutated from six entry points with no mutex
(`gateway.hpp:18-20`). The supervisor has no thread and no timer of its own —
the gateway arms the grace timers and reports every terminal frame back — so
"who is on which thread" has one answer rather than six.

**One session is one thread for its whole life.** Every QuantLib singleton is
session-local and none is declared global, so a build without
`QL_ENABLE_SESSIONS` gives two concurrent requests one process-wide
`Settings::evaluationDate()` and two silently wrong prices. With it,
`Singleton<T>::instance()` is `thread_local`
(`ql/patterns/singleton.hpp:92`), and a graph built on one thread must never be
priced on another. `Worker` constructs its `Session` *inside* `run()` for that
reason, never on the caller's thread (`worker.hpp:29-35`).

**Within a session, everything serializes.** Not merely writes: `NPV()` writes
to the lazy cache as it computes, so two nominally read-only prices on one
graph cannot overlap. Concurrency comes from more sessions, never from more
threads inside one. A hundred-strike smile is a hundred sessions or a loop —
which is why the compare panel opens a second session rather than fanning out
on the one in front of you.

**Placement is a property of the request.** A session opens in a shared worker
(eight seats by default) and moves to a sacrificial single-session process when
it asks for something long and cancellable. Moving is a close and a replay, not
a migration, because the graph is thread-bound. That is the whole reason a
`SessionLog` exists: `OpenSession` plus the accepted `UpdateMarket` frames
determine the graph completely, so a session that loses its worker is rebuilt
under the same `session_id` and the client is never told it moved.

**Every rejection names a field.** `QLS_FIELD_REQUIRE` and `QLS_FIELD_FAIL`
(`src/errors/fielderror.hpp:66,77`) raise an error carrying a wire code and the
dotted path of the field to blame; `session.cpp` uses them 204 times. That path
is what the interface highlights, and it is why nothing this build cannot price
is silently ignored — the schema is deliberately wider than the build, and the
gap between them is answered rather than approximated.

## The browser side

The client owns one thing the service does not: the **document**. Everything
else here is in service of getting it onto the wire and the answers back.

| Layer | Path | What it holds |
| --- | --- | --- |
| **Socket** | `src/protocol/client.ts` | `request_id` allocation, the pending registry, the stall watchdog, reconnection. It knows nothing about Redux |
| **Mirror** | `src/protocol/middleware.ts` | Every frame in both directions into the store. It owns no protocol |
| **Store** | `src/store/` | Thirteen slices, one per file; `workbookSlice.ts` is the document |
| **Operations** | `src/session/` | The thunks: open, price, write, sweep, book, compare, cancel |
| **Gates** | `src/protocol/capabilities.ts`, `src/market/validation.ts`, `src/trade/validation.ts` | What the service would refuse, caught before the round trip |
| **Interface** | `src/components/` | Panels and cards, none of which talk to the socket |

**The document is the workbook**, and it is the only state that survives
everything on this side: market objects, the trade, the book and the panel
state, saved to one `localStorage` key as canonical Protobuf JSON by
`store/workbookCodec.ts`. {doc}`interface` sets out the split from a user's
point of view; the developer's version of it is that `workbookSlice` is the
input to a replay, so anything that must survive a restart of the service has
to live there and nowhere else.

**Structural against live is a counter, not a guess.**
`workbook.structureRevision` counts edits that change the shape of the graph.
The session records the revision it was opened at, and the two disagreeing is
what puts the amber rebuild bar on the market pane. `UpdateMarket` carries
quotes and nothing else, so this is the whole of the distinction.

**The gates are a second copy of a fact the service owns**, which is exactly
why they are checked rather than trusted. `capabilities.ts` says what this
build offers; the service answers `Hello` with what it dispatches; `drift.ts`
diffs the two and `drift.integration.test.ts` fails on any disagreement. Only
the *sets* are compared — that an analytic barrier is European only is a
combination rule, and combination rules stay local.

**Transport scheduling is not in the store.** `session/repricer.ts` keeps at
most one write-and-price in flight and holds the latest slider value in module
state, because a drag emits far more values than the service can price and each
is superseded by the next. Putting that in Redux would make every pixel an
action with no reader.

## One price, end to end

A quote drag is the shortest path through both halves, and it touches every
layer above.

1. The slider dispatches `bumpQuote`. The workbook takes the value at once —
   the control must not lag the finger — and the latest value is queued for the
   wire (`session/repricer.ts`).
2. `writeQuotes` sends one `UpdateMarket` with the pending writes, then
   `priceCurrentTrade` sends a `Price` carrying `workbook.trade`. Both go
   through `WireClient.send`, which allocates the `request_id` and registers
   the promise that the terminal frame will settle.
3. The gateway reads the frame, checks the session, and hands it to that
   session's worker queue.
4. The worker takes it on its own thread. `UpdateMarket` writes the quotes
   behind an `UpdateGuard`, so the observer graph fires once rather than once
   per quote; `Price` builds the instrument from payoff × exercise ×
   underlying × style, chooses the engine, and calls `NPV()`. Only what depends
   on the moved quote recomputes: nothing is rebuilt.
5. The `Ack` is folded into the session log — and only on the `Ack`, which is
   what keeps the log a description of what the worker actually holds — and the
   `PriceResult` goes back with the NPV, the requested result kinds, the ones
   that were not available, and the engine echoed as it ran.
6. `middleware.ts` mirrors both frames into the store; the result pane renders
   from state, and the repricer sends whatever arrived while it was waiting.

A structural edit is the other path, and it is deliberately longer: validate,
topologically sort the market so the user never has to order it by hand, close
the old session, open a new one, and price again.

## Changing something

**Adding an option style** is the change that crosses the most seams, and the
order matters because each step is checked by the next. The basket, the most
recent one, went through all nine.

| Step | Where |
| --- | --- |
| 1. A style arm, if the schema has none | `proto/quantlib/v2/instrument.proto` |
| 2. Build it, engine by engine, and refuse the rest by field path | `ql-backend/src/session/session.cpp` |
| 3. Advertise it in the handshake | `ql-backend/src/session/capabilities.cpp` |
| 4. Price QuantLib's own reference rows over the wire | `ql-backend/test/extract_tables.py`, `test/smoke_v2.py` |
| 5. The client's tables: style, payoffs, exercises, engines, and every closure's reason | `src/protocol/capabilities.ts` |
| 6. The oneof arm and its reducers | `src/store/workbookSlice.ts` |
| 7. The controls | `src/components/trade/StyleCard.tsx` |
| 8. What to catch before the frame | `src/trade/validation.ts` |
| 9. The guide: what it accepts, and the mathematics | {doc}`trades`, {doc}`maths/exotics` |

Steps 3 and 5 are what make this safe to do in pieces: until they agree, the
drift check fails and the status bar carries a badge. Nothing depends on
remembering to do both.

**Adding a market object** is the same shape one layer down: a `MarketObject`
arm, the build in `session.cpp`, the client's editor under
`src/components/market/`, the dependency edges in `src/market/graph.ts` so the
topological sort places it, and a rule in `src/market/validation.ts` for what
the service would reject. The correlation matrix was the most recent, and
forgetting the last two of those is what made its editor unreachable for a day.

**Changing the schema** means a commit in `ql-protobuf` and a submodule bump in
both repositories, in that order. The pin is the point: a schema change that
compiles is not necessarily one that stays wire compatible.

## What the checks guard

| Suite | Run by | What it is for |
| --- | --- | --- |
| Unit | `npm test` | The pure logic: dependency extraction, the topological sort, both validators, the workbook codec |
| Integration | `npm test` | The protocol against a **running** service, not a mock. They skip when it is absent — they do not pass |
| End to end | `npm run e2e` | The interface in a real browser, with a WCAG 2 AA pass on every run |
| Reference rows | `ql-backend/test/smoke_v2.py` | 369 rows of QuantLib's published values over the wire, parsed out of its test suite rather than transcribed |

Two of them are unusual enough to be worth knowing about.
`src/lib/prose.test.ts` asserts that no identifier-shaped word appears in
rendered text, because a
mechanical rename has twice leaked out of the code and into a label, and
neither the compiler nor the linter can see that. And `workbookCodec.test.ts`
re-encodes the JSON example in {doc}`interface` and fails if this build would
export anything else, so the workbook shown in this guide cannot go stale.

## What is not there yet

Three things are known gaps rather than oversights, and all three are written
up where they belong. {doc}`limits` states them from the outside, with the rest
of what this build will not do; here is what in the code makes them true.

**Workers are threads, not processes.** `ThreadProcessHost` makes them thread
groups inside the gateway, so a kill can only disown a thread rather than end
it. A cancel that has to kill therefore leaks the work instead of stopping it,
and replay-after-death is never exercised (`DESIGN.md` §3).

**The gateway is a single point of failure.** It holds every session log in
memory, nothing here touches a disk, and losing the process loses every graph
on the box. What makes that survivable is not in the service at all: the client
holds the definition and replays it, which is why the replay path must keep
working even though resume is usually faster.

**The door is the whole of the security model.** An `Origin` check on the
upgrade, a connection cap and a session cap — no authentication, no TLS, and
loopback is not a boundary against a browser. {doc}`getting-started` has the
operational version of this.
